1. 深度解析：數據從 SQL 到記憶體的演進
Q1: XXXTable (如 NpcTable) 是 SQL Schema 嗎？
答案：不是，它是 DAO (Data Access Object) 或稱 Repository。
•
角色：它扮演著資料庫與 Java 程式碼之間的「翻譯官」。
•
職責：它包含具體的 SQL 語句（如 SELECT * FROM npc_list），並負責執行查詢。
•
關鍵動作：它將從 SQL 查到的「表格欄位（Row/Column）」轉換成 Java 虛擬機可以理解的「物件（Object）」。
Q2: Server 記憶體在用的是 "Entry" 之類的東西嗎？
答案：是的，在本專案中它們被稱為 "Templates"。
•
在 com.lineage.server.templates 包下，您可以看到如 L1Npc.java、L1Item.java。
•
關聯性：當 NpcTable 從資料庫讀取一筆資料時，它會 new L1Npc()，並將 SQL 的值賦予這個物件，最後存入記憶體中的 Map（例如 _npcs = new HashMap<Integer, L1Npc>()）。
•
用途：當玩家在遊戲中看到一隻怪物時，Server 會直接從記憶體中的這個 Map 提取 L1Npc 物件來計算數值，而不會再去翻資料庫。
Q3: 專案拆分 (Server + Entry + SQL) 的可行性？
答案：非常可行，這是典型的「分層架構」優化路徑。
•
您的構思完全符合現代軟體工程的 「職責分離（Separation of Concerns）」：
i.
Entry (或稱 Domain Models)：存放純粹的數據結構（如 L1Npc），不依賴任何資料庫庫。
ii.
SQL (或稱 Infrastructure/Persistence)：負責把 Entry 裝滿數據。底層可以是 MySQL+C3P0，也可以是 SQLite。
iii.
Server (或稱 Core Logic)：只負責拿著 Entry 進行遊戲邏輯運算。

3. 模組化拆分方案 (Proposed Modularization)
若要達成「一鍵更換資料庫（如切換至 SQLite）」，建議將專案拆分為以下三個子模組：
3.1 thor-entry (基礎數據模組)
•
內容：原 com.lineage.server.templates 下的所有類別。
•
特性：最底層，不依賴任何外部庫（如 C3P0 或 MySQL）。
•
用途：定義遊戲中所有物件的「外型」與「屬性」。
3.2 thor-sql (資料實作模組)
•
內容：原 com.lineage.server.datatables 與 DatabaseFactory。
•
特性：依賴 thor-entry。
•
擴展性：
◦
可以實作 thor-sql-mysql (依賴 C3P0)。
◦
可以實作 thor-sql-sqlite (依賴 SQLite JDBC)。
•
職責：只負責把資料從特定來源讀出來，填進 thor-entry 的物件中。
3.3 thor-server (核心邏輯模組)
•
內容：網路通訊 (Netty)、戰鬥運算、AI 邏輯。
•
特性：依賴 thor-entry 來獲取數據定義，依賴 thor-sql 的介面來觸發數據載入

4.拆分後的優勢：一鍵切換 SQLite
當專案按此架構拆分後，如果您想將資料庫改為 SQLite：
1.
Entry 層：完全不動（數據結構沒變）。
2.
Server 層：完全不動（遊戲邏輯沒變）。
3.
SQL 層：
◦
在 build.gradle 換掉 MySQL 驅動。
◦
修改 DatabaseFactory 的連線實作。
◦
結果：伺服器立刻就能從 SQLite 檔案啟動，這對於開發者在個人筆電上除錯極其方便。
